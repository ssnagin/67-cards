# План разработки 67 cards: от требований до защиты

Дата: **2 ноября 2026 года**. Целевая сдача: **31 декабря 2026 года**.

## 1. Результат, сроки и организация работы

Разработать приложение по [документу требований](https://docs.google.com/document/d/1r_w7RIxAuTG3jx8edpk0dcFL78XL3K0w-D55ILm642U/edit): наборы карточек, совместный редактор, конструктор мероприятий, шесть игровых механик, проведение сессий, восстановление соединения, безопасность и эксплуатация.

Команда — два человека, каждый выделяет 20–25 часов в неделю. Исполнители могут меняться между интерфейсом и сервером; постоянного разделения людей на frontend/backend нет. Ориентир роста — 5000 платящих пользователей; текущая целевая одновременная нагрузка — 100 игроков суммарно. Биллинг в объём не входит.

**Оценка 62 задач — 582 человеко-часа, с резервом 20% — 699 часов** (точно 698,4, округлено вверх). В согласованном тексте была арифметическая ошибка: итог 678 не совпадал с суммой строк. Состав, отдельные оценки и суммы этапов сохранены, исправлен только общий итог.

До конца декабря доступно примерно **340–430 часов на двоих**. Недостаток относительно оценки с резервом — около **269–359 часов**. Дата остаётся целевой с высоким риском переноса. Весь объём сохраняется; функции и проверки автоматически не сокращаются. Оценки предварительные и пересматриваются по фактической работе. При постоянной загрузке 40–50 командных часов в неделю полный объём с резервом потребует ориентировочно 14–17 недель, а не доступные до декабря 8–9.

### Работа с YouGile

Назначение — **существующая колонка `ToDo` внутри «ИС»**. [Указанный MCP URL](https://ru.yougile.com/data/ai/mcp) — адрес сервера подключения, не идентификатор проекта/доски/колонки. Перед записью требуется авторизованное подключение и чтение структуры; при нескольких совпадениях необходимо уточнить целевую колонку. [Инструкция подключения YouGile](https://help.yougile.com/books/baza-znanii-yougile/page/podkliucenie-mcp-chatgptclaude).

Переносить карточки с заголовком `[67C-XX] Действие и результат`, сопоставляя точный ID внутри подтверждённой области. Существующие задачи не дублировать, пользовательские изменения автоматически не затирать. Записывать возвращённые ID и проверять результат чтением. После сбоя продолжать с неподтверждённых карточек. Подробная процедура находится в [CARDS.md](CARDS.md#перенос-в-yougile). Поля `project_id`, `board_id`, `column_id` и `yougile_task_id` пока не заполнены; перенесено **0 из 62**.

### Правила ведения задач

Одна карточка — один ответственный, второй участник проверяет результат. Конкретные люди назначаются при взятии задачи. У каждого не более одной основной задачи одновременно. Оценки — суммарные человеко-часы, включающие необходимые проверки; совместная работа не уменьшает автоматически трудоёмкость.

Карточки свыше 12 часов перед началом разбиваются на подзадачи данных/контракта, серверных правил, интерфейса и интеграции. Подзадачи входят в оценку родителя. Для расширенного аукциона отдельно выделены пустые торги, способы разрешения споров и эффекты лотов.

## 2. Архитектура и правила разработки

### Размещение и компоненты

- **Frontend:** существующий Nuxt/Vue/TypeScript; клиентское приложение на GitHub Pages, без обязательного SSR. Hash-маршруты и базовый путь `/67-cards/` обеспечивают открытие вложенных экранов без серверной маршрутизации.
- **Backend:** существующий Spring Boot; модульный монолит с отдельными областями учётных записей, материалов, мероприятий, сессий и расчётов.
- **PostgreSQL:** пользователи, права, материалы, версии, шаблоны, снимки сценариев, журнал игровых команд/балансов и результаты. Подтверждённые действия сохраняются надёжно; Redis не является единственным источником истины.
- **Redis:** кэш активных сессий, присутствие и временные данные. Начальное размещение — один экземпляр; две имеющиеся реплики не считать обязательной архитектурой и не удалять из production без разрешения.
- **Совместный редактор:** Tiptap + Yjs, отдельный небольшой сервис Hocuspocus на сервере. См. [Yjs](https://docs.yjs.dev/) и [Hocuspocus](https://tiptap.dev/docs/hocuspocus/getting-started/overview).
- **Изображения:** файлы на сервере, метаданные в PostgreSQL, выдача через endpoint с проверкой доступа; резервное копирование включает файлы.
- **Внешние соединения:** HTTPS/WSS через reverse proxy. БД и Redis не публикуются в интернет.

Фронтенд остаётся на GitHub Pages, backend — на отдельном сервере по явному выбору владельца. Платежи, подписки, публичные каталоги и поиск пользователей из демо-интерфейса не превращаются в дополнительные подсистемы без отдельного требования.

### Нормализованная модель данных

Разделить:

- Учётную запись, рабочее пространство, выданные права и токены устройств.
- Набор, карточку, две стороны, вложения, совместный документ и версии.
- Мероприятие-шаблон, порядок этапов, общие поля и специфичные настройки каждого типа.
- Сессию-запуск, участника, раунд, ответ, ставку, резерв, запись баланса и результат.

Не хранить настройки всех механик в одной таблице с десятками необязательных полей. Общая сущность этапа содержит общие свойства; специфичные модели — только параметры своего режима.

Импорт карточек создаёт самостоятельные вопросы с устойчивыми ссылками на изображения. Запуск создаёт неизменяемый снимок сценария. Редактирование и удаление исходной карточки/шаблона не меняет активную игру и не уничтожает используемые снимком изображения.

Содержимое сторон имеет один авторитетный источник — совместный документ. REST не перезаписывает его устаревшим текстом. История хранит сохранённые версии с авторами; посимвольный аудит каждого нажатия не требуется. Восстановление создаёт новую версию и согласуется с активными редакторами.

### Публичные интерфейсы

- REST API `/api/v1`: авторизация, профиль, наборы, карточки, вложения, права, мероприятия, создание сессий и получение WS-билетов.
- Игровой WebSocket `/ws/game`.
- WebSocket совместного редактора `/ws/collaboration` через отдельный сервис.
- Игровая команда: `commandId`, `sessionId`, `roundId`, ожидаемая версия состояния и полезная нагрузка; конкретные типы и схемы фиксируются в 67C-04.
- Ответ сервера: ACK с результатом либо структурированная ошибка. События содержат версию и серверное время.
- REST описывается в OpenAPI; WS — схемами сообщений и примерами всех механик.
- Ведущий, игрок и общий экран получают разные проекции. Ответы, будущие скрытые этапы и внутренние настройки не отправляются игроку до разрешённого момента, в том числе при reconnect.

Для разных доменов frontend/backend: короткоживущий access-токен в памяти, обновляемый токен устройства в IndexedDB; сервер хранит его хеш, поддерживает ротацию и отзыв. API-клиент согласует параллельные запросы обновления, чтобы они не конфликтовали. Хранение в IndexedDB не заменяет защиту от XSS. WS получает короткоживущие одноразовые билеты через авторизованный REST; токены и билеты исключаются из журналов.

### Корректность игры

- Сервер определяет время, порядок команд, случайные исходы, правильность действий и баланс.
- Команды одной комнаты применяются последовательно, соседние комнаты не блокируются общей очередью.
- Повтор `commandId` возвращает прежний результат без повторного эффекта; результат критичного действия сохраняется до ACK.
- Redis можно пересоздать из PostgreSQL без потери подтверждённых ответов, ставок и балансов.
- Баллы целые; коэффициенты рассчитываются без двоичной арифметики с плавающей точкой; остатки распределения обрабатываются детерминированно.
- Резервы ставок атомарны. Нельзя потратить уже зарезервированное; при смене лидера аукциона предыдущий резерв освобождается.
- Каждая механика задаёт политику изменения действий: разрешённое изменение прогноза до закрытия не блокируется общим запретом F.5.8.
- Пауза сохраняет остаток времени; возобновление задаёт новый серверный deadline.
- Корректировки ведущего — новые записи с причиной; историю не переписывать и резервы не нарушать.
- Для модификаторов позиции фиксируются до раунда; затем рассчитываются базовый результат и применимые бонусы/штрафы, обновляется рейтинг и проверяется уменьшение баланса лидера.

### Стартовые значения и границы

- До 1000 карточек в наборе, настраивается и проверяется сервером.
- JPEG/PNG/WebP до 5 МиБ с проверкой фактического содержимого; SVG и произвольные файлы не принимаются.
- Игрок может входить без аккаунта; ведущий авторизован.
- Совместное редактирование включает одновременный ввод, курсоры, присутствие, reconnect и версии.
- Свободный ответ викторины сравнивается после нормализации регистра и пробелов с перечнем допустимых вариантов; спорный ответ оценивает ведущий.
- Общий экран только публичный, без прав управления.
- Нагрузка — 100 игроков суммарно, в том числе профиль 30 в одной комнате. Исходную формулировку NF.1.3 требуется обновить отдельно; PDF/ODT/Google Docs этой работой не изменены.
- Достаточность Raspberry Pi 5 (4 ядра, 6 ГБ RAM) подтверждается измерениями совместно работающих компонентов.

### Обязательные решения до разработки расчётов

В 67C-02 согласовать правила для неоднозначных случаев: коэффициенты рынка при пропорциональном банке, отсутствие победителей, отрицательные балансы, политика округления, ничьи, спорные ставки, принудительные ставки при пустом аукционе, эффекты лотов и сочетания модификаторов. Не объявлять эти вопросы согласованными только из-за существования этого плана.

В аукционе монетка, камень-ножницы-бумага, принудительные ставки и эффекты лотов — реальные подзадачи, а не текстовые уведомления ведущему. В рынке настройки коэффициентов не меняют незаметно пропорциональную формулу F.4.8.

## 4. Пайплайн и календарные ориентиры

### Последовательность

**Требования → контракты → основание → карточки и конструктор → техническая сессия → викторина → остальные механики → общий баланс → испытания → защита.**

Сначала провести техническую сессию с одним тестовым раундом. Затем подключать механики к общему движку; не создавать независимые системы сессий для каждого режима.

Совместный редактор — параллельная ветка после карточек и авторизации. Его сохранение и права нужно проверить до истории/импорта, а не отложить до последней недели.

### Работа вдвоём

- В начале один ведёт модель/API, второй — сценарии/интерфейс; решения проверяются совместно.
- После основания один может взять карточки/редактор, второй — мероприятия/каркас сессии; это временное разделение, а не закрепление профессий.
- После первой викторины игровые механики распределяются целиком: от настройки до результата.
- При смене задачи передаются контракт, состояние кода, выполненные проверки и ограничения.
- Изменения общего движка, балансов и прав проходят проверку напарником, чтобы разные механики не вводили несовместимые правила.

### Целевые контрольные точки

Это ориентиры с высоким риском, **не ресурсно обеспеченное обязательство** завершить все карточки к декабрю. Недостаток времени отражён в разделе 1. Даты не являются сроками всех отдельных карточек.

### Еженедельное управление

Раз в неделю вдвоём сверять завершённые карточки, фактические часы, оставшиеся оценки и блокировки. Уже после первой недели пересчитать прогноз завершения: оставшаяся трудоёмкость с резервом / доступные командные часы в неделю. При отставании фиксировать прогноз переноса и причины. Функции и проверки не вырезать без решения владельца; заглушки не учитывать как реализацию.

### Цикл задачи

1. Проверить зависимости и критерии.
2. Разбить крупную карточку на подзадачи в пределах оценки.
3. Согласовать контракт перед параллельной работой.
4. Реализовать данные, серверные правила и интерфейс.
5. Выполнить необходимые проверки, записать результаты.
6. Обновить документацию и матрицу.
7. Получить проверку напарника.
8. Закрыть со ссылкой на код/результат; отдельно выполнить разрешённую выкладку.

Production не обновляется автоматически из-за закрытия карточки или слияния кода. Имеющийся деплой из `main` необходимо привести к этому правилу в 67C-14. Текущая работа его не запускала и не меняла.

### Разрешения и серверы

Не запускать, не останавливать и не перезапускать dev-серверы без прямого запроса. Для frontend-проверок правило проекта указывает существующий 8080 с ожиданием не более 5 секунд; другое положение указывает frontend 3000, backend 16768. Это расхождение нужно уточнить в 67C-07; не переключать порты и не запускать сервер самостоятельно. При недоступности разрешённого сервера сообщить и продолжить доступные проверки.

Browser-use, Playwright и визуальные проверки выполнять только после отдельного прямого запроса пользователя («открой в браузере», «проверь визуально», «сделай скриншот», «протестируй фронтенд»). До этого — проверки кода, контрактов и серверной логики. Любые действия на production — только после подтверждения владельца.

### Основные риски и действия

- **Недостаток времени:** полный объём сохранён; еженедельный прогноз, без скрытого сокращения функциональности.
- **Совместный редактор:** проверить сохранение, авторизацию, отзыв и восстановление рано; не допускать двух конкурирующих источников текста.
- **Неоднозначные правила:** закрыть 67C-02 до расчётов; отдельно согласовать F.5.8 и изменение прогнозов.
- **Разные домены:** рано проверить токены, CORS/Origin, WSS, hash-маршруты и baseURL Pages.
- **Ограниченное железо:** нагрузить весь состав компонентов на стенде; при нехватке подготовить измерения и конкретную рекомендацию, не утверждать достаточность заранее.
- **Потеря данных:** подтверждение только после сохранения, идемпотентность, восстановление Redis из PostgreSQL, проверенное восстановление backup вместе с файлами.
- **Существующий auto-deploy:** не пушить изменения, вызывающие непроверенную production-выкладку; отделить поставку в 67C-14.
